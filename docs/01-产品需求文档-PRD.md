# 2. 产品概述

## 2.1 产品名称

码站先锋。

英文暂定名称：

Code Pioneer。

英文名称当前主要用于项目目录、代码仓库和技术标识，正式对外名称仍使用“码站先锋”。

## 2.2 产品定位

码站先锋是一款面向大学生、职业院校学生和编程初学者的编程学习微信小程序。

产品通过以下方式帮助用户学习编程：

1. 使用短章节课程讲解基础知识。
2. 使用章节小测检查学习效果。
3. 使用计时答题和人机对战增加学习兴趣。
4. 使用错题本帮助用户复习薄弱知识点。
5. 使用校园互助社区帮助用户交流问题和经验。

## 2.3 产品初衷

传统编程学习通常存在以下问题：

1. 学习内容较长，初学者容易失去耐心。
2. 只看课程但缺少练习，知识掌握不牢固。
3. 练习过程反馈较慢，缺少即时成就感。
4. 初学者遇到问题时，不知道如何提问和解决。
5. 学习过程缺少趣味性和持续动力。

码站先锋希望建立以下学习闭环：

```text
选择课程
→ 学习知识点
→ 完成章节小测
→ 参加答题练习或人机对战
→ 查看答题结果
→ 发现薄弱知识点
→ 进入错题本复习
→ 返回对应章节再次学习
```

## 2.4 核心价值

码站先锋第一版的核心价值不是提供大量课程，而是验证以下三点：

1. 用户是否愿意通过短章节学习编程知识。
2. 答题对战是否能够提升学习兴趣和练习频率。
3. 错题反馈是否能够促进用户返回课程复习。

# 3. 目标用户

## 3.1 核心用户

### 用户类型一：编程零基础学生

主要特征：

* 没有系统学习过编程。
* 不知道应该从哪里开始。
* 容易被复杂概念劝退。
* 更适合短内容和即时练习。
* 希望获得明确的学习进度。

主要需求：

* 入门课程。
* 简单示例。
* 章节小测。
* 错题解析。
* 学习进度记录。

### 用户类型二：正在学习编程的学生

主要特征：

* 已学习部分基础知识。
* 需要通过练习巩固知识。
* 希望找到学习伙伴。
* 对答题比赛和排名有兴趣。

主要需求：

* 练习模式。
* 人机对战。
* 错题本。
* 学习记录。
* 校园互助。

### 用户类型三：课程内容管理员

主要特征：

* 负责上传和维护课程内容。
* 负责录入题目及答案解析。
* 负责处理错误内容。
* 可能是管理员、教师或内容运营人员。

主要需求：

* 课程管理。
* 章节管理。
* 题库管理。
* 内容发布和下架。
* 数据查看。

### 用户类型四：社区管理员

主要特征：

* 负责维护社区内容。
* 处理用户举报。
* 删除违规帖子和评论。
* 对违规用户进行限制。

主要需求：

* 帖子管理。
* 评论管理。
* 举报处理。
* 用户状态管理。

# 4. 产品目标

## 4.1 第一版目标

第一版需要完成以下核心目标：

1. 用户能够正常进入小程序并完成账号登录。
2. 用户能够浏览和学习Python入门课程。
3. 用户能够完成章节小测。
4. 用户能够查看错误题目和答案解析。
5. 用户能够进入练习模式。
6. 用户能够完成一局人机答题对战。
7. 用户能够查看对战结果和历史记录。
8. 用户能够发布、查看和评论校园互助帖子。
9. 管理员能够维护课程、题目和社区内容。

## 4.2 第一版不追求的目标

第一版暂不追求：

* 大量课程数量。
* 多编程语言完整覆盖。
* 高并发实时竞技。
* 商业化和课程付费。
* 复杂社交关系。
* AI自动生成课程。
* AI直接代替教师答疑。
* 在线运行任意用户代码。
* 完整校园认证体系。

# 7. 用户与登录模块

## 7.1 登录方式

第一版使用微信小程序登录。

用户首次使用需要完成以下流程：

```text
进入小程序
→ 获取微信登录临时凭证
→ 后端换取用户唯一标识
→ 创建或查询用户账号
→ 返回登录凭证
→ 进入首页
```

## 7.2 登录原则

1. 微信AppSecret只能保存在后端。
2. 小程序前端不得保存微信AppSecret。
3. 登录状态由后端签发的访问令牌维护。
4. 用户访问需要登录的页面时，应检查登录状态。
5. 登录失效后，应提示用户重新登录。
6. 未登录用户可浏览公开课程和帖子。
7. 提交答案、发布帖子、评论、点赞等操作需要登录。
8. 第一版不强制小程序启动即登录，公开内容保持匿名可读，受保护功能按需触发登录流程。
9. 开发环境如启用 Mock 微信登录，仍复用正式登录接口；生产环境不得暴露第二套登录协议。

## 7.3 用户信息

第一版保存以下基础信息：

* 用户ID。
* 微信用户唯一标识。
* 昵称。
* 头像。
* 用户状态。
* 注册时间。
* 最近登录时间。
* 学习经验值。
* 对战积分。
* 连续学习天数。

## 7.4 用户状态

用户状态包括：

```text
NORMAL：正常
DISABLED：已禁用
DELETED：已注销
```

被禁用用户：

* 可以查看已有公开内容。
* 不可以发布帖子。
* 不可以发表评论。
* 不可以参加对战。
* 不可以点赞或收藏。

# 9. 课程学习模块

## 9.1 第一版课程范围

第一版只上线一门正式课程：

```text
Python编程入门
```

后端和数据库需要支持多课程，但第一版内容只维护Python入门课程。

## 9.2 课程状态

课程状态包括：

```text
DRAFT：草稿
PUBLISHED：已发布
OFFLINE：已下架
```

只有已发布课程可以在小程序中显示。

## 9.3 课程信息

课程包含：

* 课程名称。
* 课程简介。
* 课程封面。
* 课程难度。
* 预计学习时长。
* 章节数量。
* 学习人数。
* 课程状态。
* 创建时间。
* 更新时间。

## 9.4 课程详情页

课程详情页显示：

1. 课程封面。
2. 课程名称。
3. 课程简介。
4. 适合人群。
5. 学习目标。
6. 章节目录。
7. 当前学习进度。
8. 开始学习或继续学习按钮。

## 9.5 章节结构

每个课程包含多个章节。

章节包含：

* 章节名称。
* 章节简介。
* 章节排序。
* 预计学习时长。
* 是否发布。
* 是否完成。
* 章节内容。
* 章节小测。

## 9.6 章节内容类型

章节内容采用结构化内容块，不将整个章节直接保存为一段HTML。

支持以下内容块：

```text
TEXT：普通文本
HEADING：小标题
IMAGE：图片
CODE：代码块
TIP：提示信息
WARNING：注意事项
EXAMPLE：示例
QUESTION：内嵌练习题
```

其中：

* `QUESTION` 用于章节内嵌即时练习。
* 题目通过正式题库引用。
* 用户逐题提交后立即获得对错和解析反馈。
* 第一版不计入正式章节小测成绩，也不影响章节完成状态。

内容块示例：

```json
{
  "type": "CODE",
  "sort": 3,
  "content": {
    "language": "python",
    "code": "name = 'Code Pioneer'\nprint(name)"
  }
}
```

## 9.7 章节学习规则

1. 用户进入章节后记录开始学习时间。
2. 用户阅读到页面底部后，可以点击“完成本节”。
3. 如果章节存在小测，需要先完成小测才能标记为完成。
4. 有小测时，只有小测达到及格分数后才允许完成章节。
4. 完成章节后更新学习进度。
5. 再次进入已完成章节时，仍可重新学习。
6. 重新学习不会删除原有完成记录。
7. 课程进度按已完成章节数量计算。

进度计算公式：

```text
课程进度 = 已完成章节数 ÷ 已发布章节总数 × 100%
```

## 9.8 课程验收标准

1. 用户能够查看课程列表。
2. 用户能够查看课程详情。
3. 用户能够查看章节目录。
4. 用户能够进入已发布章节。
5. 章节内容按照后台配置顺序展示。
6. 代码块保留缩进和换行。
7. 图片加载失败时显示占位提示。
8. 用户完成章节后，学习进度正确更新。
9. 未发布章节不能被普通用户访问。
10. 已下架课程不能出现在课程列表中。

# 10. 题库与章节小测

## 10.1 第一版题型

第一版支持以下题型：

```text
SINGLE_CHOICE：单选题
TRUE_FALSE：判断题
CODE_OUTPUT：代码输出选择题
FILL_BLANK：填空题
CODE_INPUT：代码输入题
```

说明：

代码输出题在第一版仍采用选择答案的方式，不要求用户输入或运行代码。

填空题由服务端做标准化后比对。

代码输入题第一版只做轻量字符串匹配，不执行用户代码。

## 10.2 题目信息

每道题包含：

* 题目ID。
* 所属课程。
* 所属章节。
* 题目类型。
* 题干。
* 代码内容。
* 编程语言。
* 选项。
* 正确答案。
* 答案解析。
* 难度。
* 题目状态。
* 创建时间。
* 更新时间。

## 10.3 题目难度

题目难度包括：

```text
EASY：简单
MEDIUM：中等
HARD：困难
```

第一版章节小测以简单题和中等题为主。

## 10.4 章节小测规则

1. 每个章节配置3至10道题。
2. 小测题目由后台固定配置。
3. 用户提交后，由服务端判断答案。
4. 用户提交后不能修改本次答案。
5. 用户完成全部题目后生成小测结果。
6. 小测结果显示正确数量、错误数量和正确率。
7. 错误题目自动加入错题本。
8. 用户可以重复参加小测。
9. 每次小测都保留独立记录。
10. 章节完成状态以“小测达到及格分数”为准。
11. 未达到及格分数时保留小测记录，并允许重新测试。

## 10.5 小测结果页

显示：

* 总题数。
* 正确题数。
* 错误题数。
* 正确率。
* 获得经验值。
* 每道题的用户答案。
* 正确答案。
* 答案解析。
* 返回章节按钮。
* 查看错题按钮。
* 再测一次按钮。

## 10.6 小测验收标准

1. 用户能够正常进入章节小测。
2. 用户必须完成所有题目后才能提交。
3. 答案判断必须由服务端完成。
4. 前端不能自行决定最终得分。
5. 提交成功后生成小测记录。
6. 错题自动进入错题本。
7. 重复答错同一道题时，错题本不能生成重复题目记录。
8. 用户再次答对错题后，可更新该错题的掌握状态。
9. 请求失败时不能生成不完整记录。

# 11. 错题本模块

## 11.1 功能目标

错题本用于帮助用户集中复习答错的题目。

## 11.2 错题来源

错题可以来自：

* 章节小测。
* 练习模式。
* 人机对战。

## 11.3 错题状态

```text
UNMASTERED：未掌握
MASTERED：已掌握
```

## 11.4 错题本功能

1. 查看全部错题。
2. 按课程筛选。
3. 按章节筛选。
4. 查看题目答案和解析。
5. 重新练习错题。
6. 标记为已掌握。
7. 恢复为未掌握。

## 11.5 错题本规则

1. 同一用户、同一道题只能存在一条错题记录。
2. 重复答错时，更新错误次数和最近答错时间。
3. 用户重新答对时，系统可以自动标记为已掌握。
4. 用户可以手动修改掌握状态。
5. 删除原题后，历史错题记录不得导致页面报错。

# 12. 练习模式

## 12.1 功能目标

练习模式用于帮助用户在没有对手的情况下进行计时答题。

## 12.2 练习入口

用户可以从以下位置进入：

* 首页每日练习。
* 对战首页。
* 课程详情页。
* 章节详情页。
* 错题本。

## 12.3 练习设置

第一版支持：

* 选择课程。
* 选择章节。
* 选择题目数量。
* 选择是否计时。

题目数量可选：

```text
5题
10题
```

## 12.4 练习规则

1. 题目从已发布题库中随机抽取。
2. 同一局内题目不得重复。
3. 答案提交后显示正确与否。
4. 可以选择立即显示解析。
5. 完成全部题目后显示练习结果。
6. 错题自动加入错题本。
7. 练习不影响对战积分。
8. 练习记录需要保存。

# 13. 人机对战模块

## 13.1 功能目标

人机对战通过模拟对手答题过程，为用户提供具有竞争感的学习体验。

第一版的人机对战不接入实时真人用户。

## 13.2 对战流程

```text
进入对战页
→ 选择课程或章节
→ 点击开始对战
→ 后端创建对战记录
→ 随机生成5道题
→ 生成机器人答题数据
→ 用户逐题作答
→ 服务端计算用户得分
→ 对比机器人得分
→ 生成对战结果
```

## 13.3 对战题目

每局固定5道题。

支持题型：

* 单选题。
* 判断题。
* 代码输出选择题。

同一局内题目不得重复。

## 13.4 答题时间

每题限时15秒。

规则：

1. 页面进入题目后开始倒计时。
2. 用户提交答案后立即停止计时。
3. 超时后自动提交空答案。
4. 超时题不得分。
5. 提交后不能修改答案。
6. 进入下一题前可短暂显示正确与否。
7. 用户退出页面时，本局记录为中途退出。

## 13.5 得分规则

答对时：

```text
单题得分 = 100基础分 + 剩余整秒数 × 5
```

答错或超时：

```text
单题得分 = 0
```

示例：

用户在剩余8秒时答对：

```text
100 + 8 × 5 = 140分
```

所有分数必须由服务端计算。

前端只提交：

* 对战ID。
* 题目ID。
* 用户答案。
* 客户端答题耗时。

后端应结合服务端记录校验答题时间，避免完全相信前端数据。

## 13.6 机器人规则

第一版机器人不需要真正调用AI模型。

机器人由后端根据预设参数生成答题结果。

机器人难度包括：

```text
BEGINNER：新手
NORMAL：普通
ADVANCED：进阶
```

不同难度控制：

* 答题正确率。
* 答题时间范围。
* 是否出现连续答错。

机器人结果必须在对战开始时或服务端过程中生成，不能由小程序前端自行决定。

## 13.7 对战胜负规则

1. 总分更高的一方获胜。
2. 总分相同时，正确题数更多的一方获胜。
3. 正确题数也相同时，总答题时间更短的一方获胜。
4. 所有条件相同时，结果为平局。
5. 用户中途退出，结果为失败。
6. 系统异常导致对战无法完成时，不计胜负。

## 13.8 对战积分

第一版采用简单积分机制：

```text
初始积分：1000
胜利：+20
失败：-10
平局：+0
中途退出：-10
系统异常：+0
```

积分不能低于0。

练习模式不影响积分。

## 13.9 对战结算页

显示：

* 胜利、失败或平局。
* 用户总分。
* 机器人总分。
* 用户正确题数。
* 机器人正确题数。
* 用户总答题时间。
* 获得或扣除的积分。
* 本局题目详情。
* 答案解析。
* 再来一局按钮。
* 返回对战首页按钮。
* 查看错题按钮。

## 13.10 对战验收标准

1. 用户能够开始一局人机对战。
2. 每局生成5道不重复题目。
3. 每题倒计时为15秒。
4. 超时后自动进入下一题。
5. 每题答案只能提交一次。
6. 所有最终得分由服务端计算。
7. 对战结束后生成完整对战记录。
8. 胜负判断符合规则。
9. 积分变化符合规则。
10. 错题正确加入错题本。
11. 中途退出能够被正确记录。
12. 系统异常不得错误扣除积分。
13. 用户不能重复提交同一道题获取多次得分。

# 14. 校园互助模块

## 14.1 功能定位

校园互助是面向编程学习者的轻量交流社区。

第一版只提供基础帖子和评论功能，不开发私信和复杂关注体系。

## 14.2 帖子分类

第一版支持：

```text
HELP：问题求助
EXPERIENCE：经验分享
CHECK_IN：学习打卡
PROJECT：项目展示
TEAM：组队交流
```

## 14.3 帖子信息

每篇帖子包含：

* 帖子ID。
* 作者。
* 分类。
* 标题。
* 正文。
* 代码内容。
* 编程语言。
* 图片。
* 关联课程。
* 关联章节。
* 点赞数量。
* 评论数量。
* 浏览数量。
* 帖子状态。
* 发布时间。
* 更新时间。

## 14.4 发布帖子规则

1. 用户必须登录。
2. 用户状态必须正常。
3. 标题长度为5至50个字符。
4. 正文长度为10至5000个字符。
5. 必须选择帖子分类。
6. 最多上传9张图片。
7. 代码内容可以为空。
8. 可选择关联课程或章节。
9. 内容需要经过敏感词检查。
10. 发布成功后进入帖子详情页。

## 14.5 帖子状态

```text
PUBLISHED：正常发布
HIDDEN：已隐藏
DELETED：已删除
PENDING：待审核
```

第一版可以采用“先发布、后巡查”的方式，但命中敏感词或风险规则的内容必须进入待审核状态。

## 14.6 帖子列表

支持：

* 按发布时间排序。
* 按帖子分类筛选。
* 下拉刷新。
* 上拉加载更多。
* 查看标题、作者、摘要、发布时间、点赞数和评论数。

第一版不实现复杂个性化推荐。

## 14.7 帖子详情

显示：

* 作者信息。
* 帖子分类。
* 标题。
* 正文。
* 代码块。
* 图片。
* 发布时间。
* 点赞按钮。
* 评论入口。
* 举报入口。

## 14.8 评论功能

规则：

1. 用户必须登录。
2. 评论长度为1至1000个字符。
3. 第一版只支持对帖子的一级评论。
4. 暂不支持评论回复评论。
5. 评论需要进行敏感词检查。
6. 作者可以删除自己的评论。
7. 管理员可以删除任何违规评论。

## 14.9 点赞规则

1. 用户登录后可以点赞帖子。
2. 同一用户对同一帖子只能点赞一次。
3. 再次点击可以取消点赞。
4. 点赞数量不得出现负数。
5. 删除帖子后，相关点赞记录不再对外显示。

## 14.10 举报功能

举报对象：

* 帖子。
* 评论。

举报原因：

```text
广告推广
辱骂攻击
色情低俗
违法违规
抄袭侵权
无关内容
其他
```

用户提交举报时可以填写补充说明。

同一用户不能在短时间内重复举报同一内容。

## 14.11 社区验收标准

1. 用户能够查看帖子列表。
2. 用户能够查看帖子详情。
3. 登录用户能够发布符合规则的帖子。
4. 不符合字数规则的帖子不能提交。
5. 用户能够对帖子点赞和取消点赞。
6. 用户能够发表评论。
7. 用户能够举报帖子和评论。
8. 被隐藏或删除的帖子不能被普通用户访问。
9. 被禁用用户不能发布、评论和点赞。
10. 分页加载不能出现重复帖子。
11. 用户重复点击发布按钮不能生成多篇相同帖子。

# 18. 通用交互要求

```text
暂无错题，去完成一次练习吧。
```

## 18.5 删除确认

# 19. 数据与安全要求

## 19.1 数据原则

1. 客户端提交的数据不能直接信任。
2. 得分、胜负和积分必须由服务端计算。
3. 用户不能访问其他用户的私有数据。
4. 管理接口必须验证管理员身份和权限。
5. 数据库修改应使用迁移文件。
6. 生产环境不得使用开发测试数据。
7. 数据库不得直接暴露到公网。

## 19.2 密码和密钥

以下内容不得提交到Git仓库：

* 微信AppSecret。
* 数据库密码。
* JWT密钥。
* 对象存储密钥。
* 管理员初始密码。
* Sealos访问凭证。

项目必须提供：

```text
.env.example
```

但不能提供真实密钥。

## 19.3 输入校验

后端必须对所有输入进行校验，包括：

* 字符串长度。
* 数据类型。
* 枚举值。
* ID是否合法。
* 分页参数。
* 上传文件类型。
* 上传文件大小。
* 用户权限。
* 内容状态。

## 19.4 接口权限

接口分为：

```text
PUBLIC：无需登录
USER：普通用户登录
ADMIN：管理员登录
SUPER_ADMIN：超级管理员
```

## 19.5 日志要求

后端需要记录：

* 系统错误日志。
* 登录失败日志。
* 管理员操作日志。
* 对战异常日志。
* 关键接口异常日志。

日志不得记录：

* 用户完整访问令牌。
* 用户密码。
* 微信AppSecret。
* 数据库密码。

# 27. Codex执行约束

Codex后续开发必须遵循以下规则：

1. 只完成当前任务中明确要求的内容。
2. 不得一次性开发全部项目。
3. 不得擅自增加本文档范围外的功能。
4. 不得擅自更换已确定的技术栈。
5. 不得删除已有功能。
6. 不得修改无关文件。
7. 不得自行修改已确认的业务规则。
8. 数据库变更必须生成迁移文件。
9. 所有接口输入必须校验。
10. 所有关键接口必须进行权限检查。
11. 所有错误应返回统一格式。
12. 每次任务完成后必须输出修改文件列表。
13. 每次任务完成后必须输出运行命令。
14. 每次任务完成后必须输出测试命令。
15. 每次任务完成后必须说明未完成内容。
16. 发现需求冲突时，应停止相关实现并报告冲突。
17. 不得将真实密钥写入代码。
18. 不得为了让测试通过而删除测试。
19. 不得使用前端计算结果替代服务端业务判断。
20. 每个任务验收通过后，才能进入下一个任务。

# 29. 当前结论

码站先锋第一版采用“小步开发、逐项验收”的方式推进。

第一版的核心不是一次性完成庞大的综合平台，而是优先完成以下学习闭环：

```text
课程学习
→ 章节小测
→ 练习或人机对战
→ 查看结果
→ 错题复习
→ 返回课程
```

校园互助作为辅助功能保留，但不得影响课程与对战核心流程的开发进度。

