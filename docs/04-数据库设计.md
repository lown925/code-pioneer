# 2. 设计原则

## 2.1 数据库原则

数据库设计遵循以下原则：

1. 核心业务数据必须保存在服务端数据库中。
2. 前端只负责展示和提交操作，不作为最终数据来源。
3. 用户得分、积分、胜负等结果由服务端计算。
4. 涉及历史记录的数据优先保留，不直接物理删除。
5. 高频查询字段需要建立索引。
6. 业务唯一性不仅由代码保证，也应尽量由数据库约束保证。
7. 表名和字段名统一使用英文。
8. 表名使用 Prisma 模型单数形式。
9. 数据库表名建议使用小写下划线形式。
10. 时间统一由服务端写入。
11. 数据库时间统一保存为 UTC。
12. 前端展示时再转换为用户本地时间。
13. 不允许在数据库中保存明文密码。
14. 不允许在数据库中保存微信 AppSecret。
15. 不允许将管理员密码写入初始化脚本明文。

# 3. 命名规范

## 3.1 Prisma 模型命名

使用大驼峰：

```text
User
Course
CourseChapter
Question
BattleRecord
```

## 3.2 数据库表命名

使用小写下划线：

```text
users
courses
course_chapters
questions
battle_records
```

Prisma 中建议使用：

```prisma
@@map("users")
```

## 3.3 字段命名

Prisma 字段使用小驼峰：

```text
createdAt
updatedAt
courseId
userId
lastLoginAt
```

数据库字段可通过 `@map` 映射为小写下划线：

```prisma
createdAt DateTime @default(now()) @map("created_at")
```

## 3.4 主键

所有核心业务表统一使用：

```text
String 类型 UUID
```

Prisma 示例：

```prisma
id String @id @default(uuid())
```

不建议使用连续自增数字作为对外业务 ID。

## 3.5 时间字段

核心业务表通常包含：

```text
createdAt
updatedAt
```

需要软删除的表增加：

```text
deletedAt
```

需要发布状态的内容可增加：

```text
publishedAt
```

# 6. User 用户表

数据库表：

```text
users
```

## 6.1 用途

保存小程序普通用户的账号信息、学习基础数据和对战积分。

## 6.2 字段设计

| 字段                     | 类型          | 必填 | 默认值    | 说明         |
| ---------------------- | ----------- | -: | ------ | ---------- |
| id                     | UUID/String |  是 | uuid   | 用户主键       |
| openId                 | String      |  是 | 无      | 微信小程序用户标识  |
| unionId                | String      |  否 | null   | 微信开放平台统一标识 |
| nickname               | String      |  否 | null   | 用户昵称       |
| avatarUrl              | String      |  否 | null   | 用户头像地址     |
| status                 | UserStatus  |  是 | NORMAL | 用户状态       |
| experience             | Int         |  是 | 0      | 学习经验值      |
| battleRating           | Int         |  是 | 1000   | 对战积分       |
| continuousLearningDays | Int         |  是 | 0      | 连续学习天数     |
| lastLearningDate       | DateTime    |  否 | null   | 最近学习日期     |
| lastLoginAt            | DateTime    |  否 | null   | 最近登录时间     |
| disabledReason         | String      |  否 | null   | 禁用原因       |
| disabledAt             | DateTime    |  否 | null   | 禁用时间       |
| deletedAt              | DateTime    |  否 | null   | 注销时间       |
| createdAt              | DateTime    |  是 | now    | 创建时间       |
| updatedAt              | DateTime    |  是 | auto   | 更新时间       |

## 6.3 约束

```text
openId 唯一
unionId 非空时应唯一
battleRating 不得低于 0
experience 不得低于 0
continuousLearningDays 不得低于 0
```

## 6.4 索引

```text
openId 唯一索引
unionId 唯一索引
status 普通索引
createdAt 普通索引
lastLoginAt 普通索引
```

## 6.5 说明

第一版不主动依赖微信昵称和头像完成登录。

用户可以在登录后选择是否补充昵称和头像。

# 7. UserSession 用户会话表

数据库表：

```text
user_sessions
```

## 7.1 用途

用于管理用户登录会话、刷新令牌或令牌失效。

如果第一版采用纯短期 JWT，也可暂时简化；但建议保留会话表，为退出登录和强制下线提供支持。

## 7.2 字段设计

| 字段               | 类型       | 必填 | 说明     |
| ---------------- | -------- | -: | ------ |
| id               | UUID     |  是 | 会话主键   |
| userId           | UUID     |  是 | 用户ID   |
| refreshTokenHash | String   |  否 | 刷新令牌哈希 |
| deviceInfo       | String   |  否 | 基础设备信息 |
| ipAddress        | String   |  否 | 登录IP   |
| expiresAt        | DateTime |  是 | 会话过期时间 |
| revokedAt        | DateTime |  否 | 撤销时间   |
| createdAt        | DateTime |  是 | 创建时间   |
| updatedAt        | DateTime |  是 | 更新时间   |

## 7.3 关系

```text
User 1 —— N UserSession
```

## 7.4 安全要求

不得保存完整明文刷新令牌。

只保存：

```text
令牌哈希
```

# 9. AdminOperationLog 管理员操作日志

数据库表：

```text
admin_operation_logs
```

## 9.1 用途

记录管理员的关键后台操作。

## 9.2 字段设计

| 字段            | 类型       | 必填 | 说明           |
| ------------- | -------- | -: | ------------ |
| id            | UUID     |  是 | 日志主键         |
| adminUserId   | UUID     |  否 | 管理员ID        |
| action        | String   |  是 | 操作类型         |
| targetType    | String   |  否 | 操作对象类型       |
| targetId      | String   |  否 | 操作对象ID       |
| requestMethod | String   |  否 | 请求方法         |
| requestPath   | String   |  否 | 请求路径         |
| ipAddress     | String   |  否 | IP地址         |
| userAgent     | String   |  否 | 用户代理         |
| result        | String   |  是 | SUCCESS或FAIL |
| remark        | String   |  否 | 操作说明         |
| metadata      | Json     |  否 | 附加数据         |
| createdAt     | DateTime |  是 | 操作时间         |

## 9.3 应记录的操作

包括但不限于：

* 管理员登录。
* 创建管理员。
* 禁用管理员。
* 发布课程。
* 下架课程。
* 删除题目。
* 禁用用户。
* 隐藏帖子。
* 删除评论。
* 处理举报。

不得在 `metadata` 中保存：

* 明文密码。
* 完整令牌。

# 39. 软删除规则

以下数据优先使用软删除：

```text
User
Course
CourseChapter
ChapterContentBlock
Question
Post
Comment
FileAsset
```

## 39.1 原因

这些数据可能已被以下历史记录引用：

* 学习记录。
* 小测记录。
* 错题记录。
* 练习记录。
* 对战记录。
* 收藏。
* 举报。
* 操作日志。

直接物理删除可能破坏历史数据。

## 39.2 读取规则

普通用户查询默认增加：

```text
deletedAt IS NULL
```

内容还需检查发布状态。

## 39.3 后台删除

后台点击“删除”时，通常执行：

```text
更新 deletedAt
修改状态
```

而不是直接删除数据库行。

# 46. 数据库迁移规范

1. 不允许直接手工修改正式数据库结构。

3. 所有结构变更必须生成迁移文件。
4. 迁移文件名称要表达修改内容。
5. 不允许删除已执行迁移文件。

9. 迁移失败时不得继续部署。

# 49. Prisma开发要求

Codex编写 Prisma Schema 时必须：

1. 使用 PostgreSQL Provider。
2. 所有核心模型使用 UUID 主键。
3. 正确配置 `@relation`。
4. 正确配置级联规则。
5. 避免危险的级联物理删除。
6. 对软删除模型增加 `deletedAt`。
7. 对唯一业务关系增加 `@@unique`。
8. 对高频查询增加 `@@index`。
9. 对数据库表使用 `@@map`。
10. 对下划线字段使用 `@map`。
11. 不得使用 `Json` 代替本应建立关系的数据。
12. `Json` 字段必须有明确用途和后端校验。
13. 迁移后必须运行 Prisma Client 生成。
14. 必须提供 Seed 脚本。
15. 必须提供开发环境初始化说明。

# 54. 数据库验收标准

数据库设计实现完成后，需要满足：

1. Prisma Schema 可以通过格式检查。
2. Prisma Schema 可以成功生成 Client。
3. 初始化迁移可以成功执行。
4. PostgreSQL 中成功创建对应表。
5. 唯一约束生效。
6. 外键关系生效。
7. 核心索引已经创建。
8. Seed 脚本可以执行。
9. Seed 脚本重复执行不会生成大量重复数据。
10. 开发管理员可以创建。
11. Python测试课程可以创建。
12. 测试章节和题目可以创建。
13. 不存在明文管理员密码。
14. 不存在真实 AppSecret。
15. 不存在危险级联删除。
16. Prisma Studio 可以查看开发数据。
17. 删除和下架状态符合规则。
18. 迁移文件已经提交 Git。

# 56. 数据库开发禁止事项

Codex不得：

1. 未经确认删除已有模型。
2. 未经确认重命名核心字段。
3. 未经确认修改枚举值。
4. 使用明文密码。
5. 将正确答案直接暴露给普通题目接口。
6. 为图方便取消唯一约束。
7. 通过删除迁移解决冲突。
8. 在正式环境使用 `prisma migrate reset`。
9. 使用级联删除清空历史答题数据。
10. 将所有业务内容都放入一个 Json 字段。
11. 一次性生成所有业务服务和页面。
12. 擅自加入实时对战相关表。
13. 擅自加入付费相关表。
14. 擅自加入AI对话相关表。
15. 将测试数据混入正式环境。

# 57. 关键设计结论

码站先锋 V1.0 数据库采用以下核心设计：

```text
课程内容使用结构化内容块
题目选项独立建表
章节小测通过关联表配置题目
历史答题保存题目和答案快照
错题按用户与题目唯一
练习和对战分别保存题目快照
对战答案使用请求ID保证幂等
帖子点赞使用唯一约束
内容优先软删除
管理员操作记录日志
文件统一通过对象存储和资源表管理
```
