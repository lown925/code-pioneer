本文档用于明确码站先锋项目在Sealos上的开发、测试和正式部署方案。

本文档主要解决以下问题：

1. Sealos在项目中承担什么作用。
2. 开发、测试和正式环境如何区分。
3. PostgreSQL如何创建和连接。
4. NestJS后端如何部署。
5. Vue管理后台如何部署。

7. 环境变量如何管理。
8. 域名和HTTPS如何配置。
9. 数据库如何备份。
10. 出现部署故障时如何排查。
11. 哪些敏感信息不能提交Git或发给Codex。
12. 用户作为开发新手如何按步骤执行部署。

# 2. Sealos在本项目中的作用

码站先锋使用Sealos承载以下服务：

```text
PostgreSQL数据库
NestJS后端API
Vue管理后台
对象存储
测试环境
正式环境
```

Sealos当前提供云开发环境、应用部署、托管数据库及S3兼容对象存储等能力，适合将本项目的开发环境和部署资源集中管理。

## 2.1 第一版不强制使用的能力

第一版暂不强制使用：

* Kubernetes YAML手工部署。
* 高级自动扩缩容。
* 多副本后端。
* Redis。
* 消息队列。
* 多区域容灾。
* CI/CD自动发布。
* 灰度发布。
* 服务网格。

项目初期应优先选择简单、可理解、可恢复的部署方式。

# 3. 部署总体架构

码站先锋第一版部署结构：

```text
微信小程序
      │
      │ HTTPS请求
      ▼
NestJS后端API
      │
      ├── PostgreSQL
      │
      └── 对象存储
               
管理员浏览器
      │
      ▼
Vue管理后台
      │
      ▼
NestJS后端API
```

说明：

1. 小程序不能直接连接数据库。
2. 管理后台不能直接连接数据库。
3. 小程序和管理后台只能访问后端API。
4. 后端负责认证、权限和业务逻辑。
5. PostgreSQL只允许后端访问。
6. 对象存储由后端签发上传或访问逻辑。
7. 数据库密码不得写入前端。

# 4. 环境划分

项目必须区分以下环境：

```text
本地开发环境
Sealos测试环境
Sealos正式环境
```

## 4.1 本地开发环境

用途：

* Codex编写代码。
* VS Code开发。
* 单元测试。
* 快速调试。
* Prisma迁移开发。
* 微信开发者工具调试。

环境标识：

```text
development
```

数据特点：

* 可以使用Mock用户。
* 可以使用测试课程。
* 可以重置本地数据库。
* 可以开放Swagger。
* 不保存真实用户数据。

## 4.2 Sealos测试环境

用途：

* 前后端联调。
* 真机测试。
* 内部测试。
* 验证部署流程。
* 验证HTTPS和域名。
* 验证对象存储。
* 验证数据库迁移。

环境标识：

```text
test
```

测试环境允许：

* 测试管理员。
* 测试用户。
* 测试课程。
* 测试帖子。
* Mock登录，但必须明确限制为测试环境。

测试环境不得：

* 使用正式数据库。
* 使用正式密钥。
* 接收正式用户。
* 与正式环境共享管理员密码。

## 4.3 Sealos正式环境

用途：

* 微信小程序正式用户。
* 正式管理后台。
* 正式课程和题目。
* 正式业务数据。

环境标识：

```text
production
```

正式环境要求：

* 禁止Mock登录。
* 使用独立数据库。
* 使用独立对象存储目录或Bucket。
* 使用强随机密钥。
* 开启HTTPS。
* 限制Swagger。
* 配置数据库备份。
* 使用正式微信AppID和AppSecret。
* 不保留测试数据。

# 5. 环境资源命名规范

为了避免混淆，资源名称必须带环境标识。

## 5.1 测试环境

建议名称：

```text
code-pioneer-test-api
code-pioneer-test-admin
code-pioneer-test-postgres
code-pioneer-test-storage
```

## 5.2 正式环境

建议名称：

```text
code-pioneer-prod-api
code-pioneer-prod-admin
code-pioneer-prod-postgres
code-pioneer-prod-storage
```

## 5.3 禁止名称

不建议使用：

```text

server
database

final2
```

名称应能直接判断：

* 属于哪个项目。
* 属于哪个环境。
* 是什么服务。

# 6. Sealos账号和区域

## 6.1 账号原则

建议使用长期可控制的账号注册Sealos。

不要使用：

* 临时邮箱。
* 他人账号。
* 无法找回的账号。
* 只由Codex掌握的账号。

## 6.2 区域选择

创建资源时尽量保持：

```text
后端
数据库
对象存储
```

位于同一Sealos区域。

原因：

* 降低服务间延迟。
* 减少跨区域网络问题。
* 简化排查。
* 可能减少流量成本。

## 6.3 区域不得随意变更

创建正式数据库后，不得因看到其他区域价格变化就随意迁移。

正式迁移需要：

* 备份。
* 恢复测试。
* 修改连接配置。
* 停机计划。
* 完整回归。

# 7. 费用控制原则

用户目前处于项目开发初期，因此资源配置应从小规格开始。

建议：

```text
测试环境：
低配置
单副本
按实际开发时间运行

正式初期：
小规格
单副本或平台支持的基础可靠方案
根据真实用户量再扩容
```

Sealos创建数据库时通常可以选择CPU、内存、存储和副本数量，并在部署前查看预计费用。开发和测试阶段可使用单副本小规格，但正式环境的具体资源应在上线前根据预算和实际压力重新评估。

## 7.1 防止意外费用

应定期检查：

* 正在运行的DevBox。
* 未使用数据库。
* 无用应用。
* 过大存储。
* 公网流量。
* 测试资源。
* 备份文件数量。

## 7.2 删除资源前

删除任何Sealos资源前必须确认：

1. 是否为测试环境。
2. 是否有重要数据。
3. 是否已备份。
4. 是否有其他服务正在连接。
5. 资源名称是否看清楚。
6. 是否会影响正式环境。

# 8. PostgreSQL部署方案

Sealos官方数据库文档支持通过数据库应用创建PostgreSQL，并在部署完成后提供连接信息。官方示例中可选择数据库版本、CPU、内存、副本和存储大小。

## 8.1 开发顺序

数据库部署顺序：

```text
先创建测试数据库
→ 后端测试连接
→ 执行迁移
→ 导入测试数据
→ 完成联调
→ 上线前再创建正式数据库
```

不要一开始就创建正式数据库进行日常开发。

## 8.2 创建测试PostgreSQL

进入Sealos数据库应用后：

1. 点击创建数据库。
2. 选择PostgreSQL。
3. 选择平台当前提供的稳定版本。
4. 输入数据库资源名称。
5. 配置CPU和内存。
6. 设置存储容量。
7. 测试环境选择单副本。
8. 查看预计费用。
9. 确认创建。

数据库名称建议：

```text
code_pioneer_test
```

用户名由平台生成或自行设置。

## 8.3 PostgreSQL版本

不要只因版本号最大就盲目选择。

选择原则：

1. Prisma当前版本支持。
2. Node.js PostgreSQL驱动支持。
3. Sealos提供稳定托管。
4. 不选择已停止维护版本。
5. 测试和正式环境尽量一致。

正式部署时再根据Sealos控制台实际可选版本确认。

## 8.4 获取连接信息

数据库创建成功后，需要保存：

```text
主机地址
端口
数据库名称
用户名
密码
内部连接地址
外部连接地址，如平台提供
```

优先使用：

```text
Sealos内部网络连接地址
```

前提是后端和数据库处于同一区域及可互通网络。

## 8.5 DATABASE_URL

Prisma使用：

```text
DATABASE_URL
```

格式示例：

```text
postgresql://USERNAME:PASSWORD@HOST:PORT/DATABASE?schema=public
```

注意：

* 示例不能填写真实密码。
* 密码有特殊字符时需要URL编码。
* 不得将完整连接字符串截图公开。
* 不得提交到Git。

## 8.6 测试数据库环境变量

测试环境：

```text
DATABASE_URL=测试数据库连接字符串
NODE_ENV=test
```

正式环境：

```text
DATABASE_URL=正式数据库连接字符串
NODE_ENV=production
```

两者不得相同。

# 9. 数据库网络安全

## 9.1 基本原则

PostgreSQL不应直接暴露给微信小程序或管理后台。

允许连接方：

```text
NestJS后端
管理员经过授权的维护工具
必要的迁移任务
```

## 9.2 公网访问

若Sealos数据库支持公网访问，原则上：

```text
测试和正式后端优先使用内部连接
```

只有以下情况才临时使用外部连接：

* 本地开发连接测试数据库。
* 手工数据库维护。
* 数据迁移。
* 故障排查。

用完后应关闭或限制公网访问。

## 9.3 数据库账号

测试和正式环境必须使用不同账号或不同数据库实例。

不得：

* 所有环境共用同一密码。
* 将超级管理员数据库账号长期用于所有业务。
* 在群聊中发送数据库密码。
* 将密码保存到文档。

# 10. Prisma迁移部署

## 10.1 开发环境迁移

本地开发时使用：

```bash
npx prisma migrate dev --name migration_name
```

仅适用于开发数据库。

## 10.2 测试和正式环境迁移

部署环境使用：

```bash
npx prisma migrate deploy
```

不得在正式环境使用：

```bash
npx prisma migrate reset
```

## 10.3 正式迁移步骤

正式环境迁移必须按以下顺序：

```text
数据库备份
→ 确认当前后端版本
→ 检查迁移文件
→ 在测试环境执行迁移
→ 测试通过
→ 正式环境执行 migrate deploy
→ 检查迁移结果
→ 启动新后端版本
→ 执行核心回归测试
```

## 10.4 迁移失败

迁移失败时：

1. 不继续启动新版本。
2. 保存完整日志。
3. 不删除迁移文件。
4. 不执行reset。
5. 检查数据库状态。
6. 将报错发给ChatGPT分析。
7. 必要时恢复备份。

# 11. NestJS后端部署方式

后端可以通过Sealos的云开发或应用部署能力运行。Sealos官方说明其DevBox支持预配置运行环境、连接本地IDE、配置容器端口、公网访问和平台子域名，也可继续构建部署应用。

第一版建议采用：

```text
代码仓库
→ 构建NestJS
→ 运行生产命令
→ Sealos公开HTTPS域名
```

## 11.1 后端生产要求

NestJS生产环境必须：

* 使用编译后的JavaScript。
* 不使用开发监听模式。
* 使用生产环境变量。
* 执行数据库迁移。
* 提供健康检查。
* 监听平台指定端口。
* 监听 `0.0.0.0`。
* 不只监听localhost。

## 11.2 端口

后端默认端口建议：

```text
3000
```

代码应支持：

```text
PORT
```

示例逻辑：

```text
优先使用环境变量PORT
没有时开发环境默认3000
```

不得把Sealos端口写死在多个文件中。

## 11.3 启动命令

生产构建：

```bash
npm ci
npx prisma generate
npm run build
```

迁移：

```bash
npx prisma migrate deploy
```

启动：

```bash
npm run start:prod
```

实际命令应以项目 `package.json` 为准。

## 11.4 后端健康检查

部署后检查：

```text
GET /api/v1/health
```

预期：

```json
{
  "success": true,
  "data": {
    "status": "ok"
  }
}
```

还应检查：

```text
GET /api/v1/health/ready
```

确认数据库连接。

# 13. 环境变量安全

## 13.1 可以提交Git的文件

```text
.env.example
```

内容只能包含字段名和说明。

示例：

```text
DATABASE_URL=
JWT_SECRET=
WECHAT_APP_ID=
WECHAT_APP_SECRET=
```

## 13.2 不得提交Git

```text
.env
.env.local
.env.test.local
.env.production
包含真实密钥的配置文件
```

## 13.3 检查Git

部署前执行：

```bash
git status
git diff
```

并搜索敏感字段：

```text
DATABASE_URL
JWT_SECRET
WECHAT_APP_SECRET
SECRET_KEY
ACCESS_KEY
PASSWORD
```

## 13.4 密钥意外提交

一旦真实密钥提交Git：

1. 不能只删除代码中的字符串。
2. 立即更换密钥。
3. 视原密钥为已泄漏。
4. 检查Git历史。
5. 必要时清理历史。
6. 检查是否被外部使用。
7. 记录安全事件。

# 14. 后端域名与HTTPS

微信小程序正式请求要求使用合适的HTTPS服务域名。

后端测试域名示例：

```text
https://test-api.example.com
```

正式域名示例：

```text
https://api.example.com
```

## 14.1 Sealos默认域名

开发和早期测试阶段可以使用Sealos提供的默认子域名。

Sealos DevBox文档说明，开启公网访问后平台可提供子域名，也支持配置自定义域名。

## 14.2 正式自定义域名

正式上线建议使用自己的域名。

优点：

* 品牌统一。
* 方便微信后台配置。
* 将来迁移平台更容易。
* 接口地址更稳定。

## 14.3 HTTPS检查

部署后检查：

* 浏览器无证书警告。
* 证书未过期。
* 域名匹配。
* HTTP能够跳转HTTPS或直接禁用。
* 小程序真机可访问。
* 上传域名可访问。

# 15. CORS配置

## 15.1 小程序

微信小程序请求不完全等同于浏览器CORS，但仍应配置安全的API访问规则。

## 15.2 管理后台

后端必须允许管理后台域名。

测试示例：

```text
https://test-admin.example.com
```

正式示例：

```text
https://admin.example.com
```

## 15.3 禁止生产环境全部放开

正式环境不建议长期使用：

```text
Access-Control-Allow-Origin: *
```

应配置明确允许列表。

环境变量示例：

```text
CORS_ORIGINS=https://admin.example.com
```

# 16. Vue管理后台部署

管理后台属于静态前端应用。

部署流程：

```text
安装依赖
→ 设置API地址
→ 构建
→ 部署dist目录
→ 配置HTTPS域名
```

## 16.1 构建命令

```bash
cd admin-web
npm ci
npm run build
```

构建产物通常位于：

```text
admin-web/dist
```

## 16.2 管理后台环境变量

Vite变量示例：

```text
VITE_API_BASE_URL
VITE_APP_ENV
```

测试环境：

```text
VITE_API_BASE_URL=https://test-api.example.com/api/v1
VITE_APP_ENV=test
```

正式环境：

```text
VITE_API_BASE_URL=https://api.example.com/api/v1
VITE_APP_ENV=production
```

## 16.3 前端变量安全

注意：

```text
所有VITE_开头变量都会进入前端构建结果
```

因此不得放入：

* 数据库密码。
* JWT密钥。
* 微信AppSecret。
* 对象存储Secret Key。
* 管理员密码。

前端只能保存公开API地址等非敏感配置。

## 16.4 管理后台路由刷新

Vue Router使用History模式时，需要配置：

```text
所有前端路由回退到index.html
```

否则刷新：

```text
/courses
/users
/reports
```

可能出现404。

## 16.5 管理后台域名

测试：

```text
https://test-admin.example.com
```

正式：

```text
https://admin.example.com
```

后台不建议与普通小程序API使用完全相同子域名。

# 17. 对象存储部署

Sealos当前平台说明包含S3兼容对象存储能力，可用于保存课程封面、章节图片、帖子图片和反馈图片。

## 17.1 对象存储用途

保存：

```text
课程封面
章节内容图片
帖子图片
反馈图片
用户头像
```

不保存：

* 用户密码。
* JWT密钥。
* 数据库备份公开链接。
* 任意可执行文件。
* 后端源代码私密配置。

## 17.2 Bucket划分

推荐两种方案。

### 方案一：环境独立Bucket

```text
code-pioneer-test
code-pioneer-prod
```

优点：

* 隔离明确。
* 正式数据不易被测试误删。

推荐采用。

### 方案二：同一Bucket不同前缀

```text
test/
prod/
```

不推荐新手初期使用，容易配置错误。

## 17.3 文件目录

建议存储Key：

```text
course-covers/YYYY/MM/uuid.webp
chapter-images/YYYY/MM/uuid.webp
post-images/YYYY/MM/uuid.webp
feedback-images/YYYY/MM/uuid.webp
avatars/YYYY/MM/uuid.webp
```

不得直接使用用户原始文件名。

## 17.4 上传流程

第一版推荐：

```text
用户选择图片
→ 小程序或后台上传到NestJS
→ NestJS校验文件
→ NestJS上传对象存储
→ 创建FileAsset记录
→ 返回fileId和访问地址
```

暂不直接让小程序持有对象存储密钥。

## 17.5 文件校验

后端必须检查：

* 文件扩展名。
* MIME类型。
* 文件真实内容。
* 文件大小。
* 图片尺寸。
* 上传数量。
* 用户权限。

## 17.6 访问权限

第一版公开课程图、帖子图可以采用公开读取地址。


## 25.3 手工备份命令示意

使用PostgreSQL工具：

```bash
pg_dump -Fc -h HOST -p PORT -U USER -d DATABASE -f backup.dump
```

此命令只是格式示例。

实际执行时不得把密码直接写进命令历史。

## 25.4 恢复命令示意

```bash

```

恢复前必须：

* 创建目标数据库。
* 确认环境。
* 确认不会覆盖正式数据。
* 先在测试环境验证。

## 25.5 备份不是完成条件

只有实际验证过恢复，备份才可信。

至少在上线前完成一次：

```text

→ 恢复
→ 检查课程和用户数据
```

# 35. 回滚原则

## 35.1 应用回滚

若新版本出现严重Bug：

```text
停止继续发布
→ 恢复上一稳定镜像或版本
→ 检查数据库兼容性
→ 验证健康接口
→ 记录问题
```

## 35.2 数据库回滚

数据库迁移不能简单依赖应用回滚。

如果新版本迁移改变数据结构：

* 先评估旧应用是否兼容新结构。
* 必要时编写反向迁移。
* 严重情况下从备份恢复。
* 不直接删除表或字段。

## 35.3 向后兼容

重要迁移优先采用：

```text
先新增字段
→ 新旧代码兼容
→ 数据迁移
→ 稳定后再移除旧字段
```

第一版规模较小时也应养成这一习惯。

# 36. 常见部署故障排查

## 36.1 后端无法启动

检查：

* 启动命令。
* Node版本。
* PORT。
* 环境变量。
* Prisma Client是否生成。
* 数据库连接。
* 依赖是否安装。
* 构建是否成功。

## 36.2 数据库连接失败

检查：

* DATABASE_URL。
* 主机地址。
* 端口。
* 用户名。
* 密码。
* 数据库名称。
* 网络访问权限。
* 密码特殊字符编码。
* 数据库是否正在运行。

## 36.3 健康接口404

检查：

* API前缀是否为 `/api/v1`。
* Health模块是否导入。
* 实际容器端口。
* 域名是否指向正确应用。
* 是否部署了旧版本。

## 36.4 管理后台刷新404

检查：

* 是否配置SPA回退。
* Vue Router模式。
* 静态服务配置。
* 构建目录是否正确。

## 36.5 小程序请求失败

检查：

* HTTPS。
* 合法域名。
* API地址。
* 证书。
* 请求路径。
* Token。
* CORS或服务端限制。
* 真机是否仍使用localhost。

## 36.6 图片上传失败

检查：

* 上传域名。
* 文件大小。
* MIME类型。
* 对象存储环境变量。
* Bucket权限。
* 后端日志。
* 临时文件处理。
