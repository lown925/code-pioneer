## 课时 1：从一行代码走到真实硬件

课时简介：认识软件和硬件之间并不是“一步到位”。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
你写下 `print("Hi")` 时，CPU 并不认识 Python 关键字。程序必须经过解释器或编译器、操作系统和硬件，最后才变成屏幕上的字符。

[标题]
先建立一个能看见的模型

[文本]
可以把执行路径看成一条接力链：源代码表达“想做什么”，运行时把它翻译成更低层操作；操作系统负责申请资源；CPU 执行指令；内存保存正在使用的数据；设备最终完成输出。每一层都只解决自己负责的问题。

[代码 language=text]
Python 源代码
  ↓ 解释器/运行时
机器指令与系统调用
  ↓
操作系统分配 CPU / 内存 / 设备
  ↓
CPU 执行 + 内存保存数据
  ↓
终端显示 Hi
[/代码]

[文本]
当程序要求输出时，运行时会准备字符串数据，并通过操作系统提供的接口把输出请求交给终端设备。这里“程序”“操作系统”“CPU”不是同一个东西：程序描述任务，操作系统管理资源，CPU 真正执行机器指令。

  ↓

CPU 执行 + 内存保存数据
  ↓
终端显示 Hi
[/示例]

## 课时 2：CPU、内存和磁盘各自负责什么

课时简介：区分三个经常被混在一起的硬件角色。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
初学者常说“电脑内存不够所以文件没了”或“CPU 保存程序”。这些说法混淆了计算、临时工作区和长期存储。

[标题]
先建立一个能看见的模型

[文本]
CPU 主要负责执行指令和计算；内存保存正在运行程序需要快速访问的数据，断电后通常丢失；磁盘/SSD 用于长期保存文件，速度远慢于 CPU 和内存，但容量更大。

[代码 language=text]
CPU：执行 add / compare / jump
内存：保存当前代码、变量、栈、缓存数据
SSD：保存程序文件、照片、数据库文件

速度：CPU寄存器 > Cache > 内存 > SSD
容量：通常反过来
[/代码]

[文本]
打开一个 500MB 程序时，程序文件长期存在 SSD；运行后部分代码和数据被读入内存；CPU 再从更靠近自己的位置取指令执行。程序关闭后，内存中的工作状态可能消失，但 SSD 上的程序文件仍然存在。

容量：通常反过来
[/示例]

[提示 title=判断自己是不是真的理解]
把示例中的数字、名称或输入换掉，再独立推导一次。如果还能解释每一步，说明你理解的是规则而不是答案。

[警告 title=常见错误]
把内存和磁盘都称为“存储”后就认为二者可以互换。它们在速度、容量、是否易失和使用方式上差别很大。

[标题]
本课小结

[文本]
能根据“计算、临时工作、长期保存”选择 CPU、内存或磁盘。

## 课时 3：指令和数据为什么都能放在内存

课时简介：理解冯·诺依曼式“存储程序”直觉。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
如果指令只能焊死在硬件里，每换一个程序就要改机器。现代计算机把程序指令也编码成二进制，像数据一样放进内存。

[标题]
先建立一个能看见的模型

[文本]
内存本质上保存一串位。某段位被当作“指令”还是“数据”，取决于 CPU 当前把它当作什么来解释。程序计数器指向的位置会被作为下一条指令读取，而 load 指令读取的位置则可能被当作普通数据。

[代码 language=text]
内存地址 1000: 0010 0001   ← CPU 当前把它当作指令
内存地址 1001: 0000 0101   ← 可能是下一条指令/立即数
内存地址 5000: 0000 1010   ← 程序把它当作数据 10
[/代码]

[文本]
“都是二进制”不等于“没有区别”。区别来自上下文：CPU 的控制逻辑根据指令格式解释取指位置的比特；程序通过读写指令访问其他地址的数据。

[示例 title=最小可验证示例]
说明：用最小输入观察本课核心规则。
语言：text

内存地址 1001: 0000 0101   ← 可能是下一条指令/立即数
内存地址 5000: 0000 1010   ← 程序把它当作数据 10
[/示例]

[提示 title=判断自己是不是真的理解]
把示例中的数字、名称或输入换掉，再独立推导一次。如果还能解释每一步，说明你理解的是规则而不是答案。

[警告 title=常见错误]
认为某个二进制值天生就是“代码”或“数据”。同一串比特在不同解释规则下可以有不同含义。

[标题]
本课小结

[文本]
理解存储程序思想，并能解释“位本身没有语义，解释方式决定语义”。

## 课时 4：操作系统为什么夹在程序和硬件之间

课时简介：理解 OS 不是“一个桌面界面”，而是资源管理和抽象层。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
如果每个应用都直接控制磁盘扇区、网卡寄存器和物理内存，不同程序会互相覆盖数据，也很难兼容不同硬件。

[标题]
先建立一个能看见的模型

[文本]
操作系统把复杂硬件封装成较稳定的抽象：应用看到文件而不是磁盘扇区，看到进程虚拟地址而不是随便写物理内存，看到 socket 而不是直接驱动网卡。OS 同时负责权限和资源分配。

[代码 language=text]
应用程序
  ├─ open/read/write → “文件”抽象
  ├─ malloc/虚拟地址 → “内存”抽象
  └─ socket → “网络端点”抽象
        ↓
      操作系统
        ↓
磁盘 / 内存 / 网卡 / CPU
[/代码]

[文本]
这样做带来两个好处：应用更容易编写，不必知道具体硬件细节；不同程序也能被隔离，不能随意覆盖彼此资源。系统调用就是应用向内核请求受控服务的入口。

  └─ socket → “网络端点”抽象
        ↓
      操作系统
        ↓
磁盘 / 内存 / 网卡 / CPU
[/示例]

## 课时 5：一次 print 背后的系统协作

课时简介：把前面四个概念串成一次真实执行。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
只有把抽象概念串成完整路径，才知道“CPU、内存、OS”不是几个孤立名词。我们追踪一次最简单的输出。

[标题]
先建立一个能看见的模型

[文本]
程序中的字符串先存在进程可访问的内存区域；运行时准备输出请求；通过系统调用进入内核；内核检查目标输出设备并把数据交给驱动；CPU 在整个过程中执行相关指令，设备最终呈现字符。

[代码 language=text]
print("Hi")
  ↓ 字符串位于进程内存
运行时准备 write 请求
  ↓ 系统调用
内核 → 终端驱动 → 显示设备
  ↓
屏幕出现 Hi
[/代码]

[文本]
注意不是“一条 print 指令让屏幕亮起来”。高级语言调用、内存中的字符串、系统调用、内核和驱动共同完成任务。追踪路径时可以不断问：“此刻数据在哪里？下一步是谁接手？”

## 课时 6：用分层视角定位性能问题

课时简介：学会遇到“慢”时先确定是哪一层慢。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
“程序慢”可能是 CPU 计算多、内存访问差、磁盘 I/O 慢、网络等待，甚至锁竞争。直接升级 CPU 可能完全没有效果。

[标题]
先建立一个能看见的模型

[文本]
定位性能问题的第一步不是猜硬件，而是观察时间花在哪里。CPU 使用率长期接近满载且计算密集，可能受 CPU 限制；CPU 很空但大量等待磁盘或网络，则更像 I/O 瓶颈。

[代码 language=text]
现象 A：CPU 98%，磁盘低 → 先查计算热点
现象 B：CPU 10%，磁盘队列很长 → 先查磁盘 I/O
现象 C：CPU 低，网络 RTT 很高 → 先查网络等待
[/代码]

[文本]
分层分析能减少“头痛医头”。系统课程后面会继续给出 Cache miss、缺页、中断、上下文切换等更细指标，但现在先建立“现象 → 层次 → 证据”的思路。
