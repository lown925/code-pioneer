## 课时 3：哈希和数字签名

课时简介：区分“摘要”和“谁签的”。
预计学习时间：12-18 分钟

### 正文

[标题]
为什么现在需要它

[文本]
哈希把任意长度数据映射为固定长度摘要，用于检测变化；但单独哈希不能证明消息来自谁，因为攻击者也能改内容后重新算哈希。数字签名使用私钥对消息/摘要签名，验证者用公钥验证。

[标题]
先建立一个能看见的模型

[文本]
发布者对软件摘要签名。用户下载软件后重新计算哈希并验证签名：内容被改会导致摘要不匹配，攻击者没有合法私钥也难以伪造签名。

[代码 language=text]
message → hash → digest
digest + private key → signature

receiver:
message → hash
signature + public key → verify
[/代码]

[文本]
哈希不是加密：通常不能从摘要还原原文。签名也通常不是为了隐藏内容，而是提供完整性和来源证明。

语言：text

digest + private key → signature

[/示例]

### 正文

[标题]
为什么现在需要它

[文本]
服务器直接说“这是我的公钥”不够，因为中间人也能这么说。数字证书把域名、公钥等信息与受信任CA的签名绑定。

[标题]
先建立一个能看见的模型

[文本]
浏览器验证服务器证书：域名是否匹配、有效期、签名能否沿中间CA链到系统信任的根CA。通过后，浏览器才更有理由相信当前公钥属于目标站点。

[代码 language=text]
Root CA (trusted)
   ↓ signs
Intermediate CA
   ↓ signs
example.com certificate
   contains: domain + public key
[/代码]

[文本]
根CA信任通常来自操作系统/浏览器预置策略。证书过期、域名不匹配、链断裂都会触发警告。

[标题]
为什么现在需要它

[文本]
TLS握手必须解决“对方是谁”“双方用什么算法”“如何得到共享密钥”。之后才能高效保护HTTP数据。

[标题]

[文本]

[代码 language=text]
ClientHello -------->
           <-------- ServerHello + cert + proof
verify certificate
derive shared keys
<====== encrypted application data ======>
[/代码]

[文本]
真实TLS1.3细节更多，但不要把握手记成死顺序。核心是“协商+认证+密钥建立”。
