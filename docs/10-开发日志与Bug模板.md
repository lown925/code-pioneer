# 1. 文档目的

本文档用于统一码站先锋项目的开发记录方式。

开发日志不是为了形式，而是为了回答以下问题：

1. 当前项目做到哪一步。
2. 哪个任务由Codex完成。
3. Codex修改了哪些内容。
4. 执行了哪些命令。
5. 测试是否通过。
6. 当前有哪些Bug。
7. Bug是否已经修复。
8. 哪个Git提交对应哪个任务。
9. 当前版本新增或修改了什么。
10. 出现问题时如何快速回退和定位。

项目正式开发后，每完成一个任务，都必须更新开发日志。

# 2. 需要建立的记录文件

项目 `docs` 目录中需要建立：

```text
docs/
├── 开发日志.md
├── Bug记录.md
└── 更新日志.md
```

三个文件用途不同。

## 2.1 开发日志

记录：

* 每个开发任务。
* Codex执行情况。
* 测试结果。
* Git提交。
* 遗留问题。
* 下一步安排。

## 2.2 Bug记录

记录：

* 问题表现。
* 复现步骤。
* 严重程度。
* 修复状态。
* 修复提交。
* 验证结果。

## 2.3 更新日志

记录：

* 每个版本新增了什么。
* 修改了什么。
* 修复了什么。
* 是否存在数据库迁移。
* 部署和回滚信息。

# 3. 开发日志使用原则

## 3.1 一个任务一条记录

每个任务编号对应一条开发记录。

例如：

```text
ENV-001
INIT-001
BACKEND-001
DATABASE-001
```

不得将多个未验收任务混在一条记录中。

## 3.2 先记录任务，再记录结果

任务开始时可以先创建记录，状态为：

```text
IN_PROGRESS
```

任务完成并验收后更新为：

```text
DONE
```

## 3.3 如实记录

不得为了让项目看起来顺利而隐藏：

* 测试失败。
* 未执行的命令。
* 已知问题。
* 临时方案。
* 未完成内容。
* 数据库风险。

## 3.4 日志不保存敏感信息

开发日志中不得写入：

* 数据库密码。
* 完整DATABASE_URL。
* JWT密钥。
* 微信AppSecret。
* 对象存储Secret Key。
* 管理员密码。
* 完整访问令牌。

# 6. 任务状态更新规则

开发日志中任务状态必须与开发任务清单一致。

状态说明：

```text
TODO：未开始
READY：可以开始
IN_PROGRESS：Codex正在执行
BLOCKED：存在阻断
REVIEW：等待ChatGPT审查
TESTING：用户正在测试
DONE：验收并提交Git
CANCELLED：取消
````

## 6.1 状态变更示例

```text
READY
→ IN_PROGRESS
→ REVIEW
→ TESTING
→ DONE
```

## 6.2 出现问题

```text
IN_PROGRESS
→ BLOCKED
```

问题解决后：

```text
BLOCKED
→ IN_PROGRESS
```

# 7. Codex结果归档

Codex任务完成后，应将其结果摘要写入开发日志。

至少记录：

1. 完成了什么。
2. 修改了哪些文件。
3. 新增了哪些文件。
4. 是否增加依赖。
5. 是否修改数据库。
6. 是否新增接口。
7. 执行了哪些命令。
8. 哪些测试通过。
9. 哪些测试没有执行。
10. 有哪些已知问题。

不建议把Codex特别长的完整回复全部复制到开发日志。

保留摘要即可。

若完整回复很重要，可以另存：

```text
docs/codex-records/
```

例如：

```text
docs/codex-records/INIT-002.md
```

第一版暂不强制建立该目录。

# 8. Git提交登记

每个通过验收的任务都应记录Git提交。

## 8.1 提交信息格式

```text
type(scope): description
```

例如：

```text
chore(project): initialize project structure
feat(health): add backend health endpoint
feat(auth): add user authentication
fix(battle): prevent duplicate scoring
```

## 8.2 需要记录的内容

```text
提交信息
Commit Hash
提交日期
对应任务编号
测试结果
```

## 8.3 获取Commit Hash

提交后执行：

```bash
git log -1 --oneline
```

将结果写入开发日志。

# 9. Bug编号规范

Bug统一使用：

```text
BUG-001
BUG-002
BUG-003
```

编号递增，不重复使用。

即使Bug后来被判定为重复或无需修复，也保留编号。

# 10. Bug严重程度

## P0 致命

包括：

* 系统无法启动。
* 数据丢失。
* 严重越权。
* 密钥泄漏。
* 正式数据库损坏。
* 用户可以无限刷积分。
* 大量用户无法使用。

处理：

```text
立即停止当前开发或上线
优先修复
```

## P1 严重

包括：

* 无法登录。
* 无法学习。
* 无法提交小测。
* 无法完成对战。
* 管理员无法发布课程。
* 重复提交导致严重重复数据。
* 核心积分计算错误。

处理：

```text
当前阶段不得验收
上线前必须修复
```

## P2 一般

包括：

* 筛选错误。
* 局部功能异常。
* 非核心页面报错。
* 错误提示不正确。
* 部分异常状态未处理。

处理：

* 原则上当前阶段修复。
* 特殊情况下可记录后集中处理。

## P3 轻微

包括：

* 文案问题。
* 间距问题。
* 轻微样式错位。
* 不影响使用的小体验问题。

处理：

* 记录。
* 后续UI优化处理。

# 11. Bug状态规范

```text
NEW
CONFIRMED
IN_PROGRESS
FIXED
REOPENED
CLOSED
WONT_FIX
DUPLICATE
```

含义：

* `NEW`：新发现。
* `CONFIRMED`：已确认可以复现。
* `IN_PROGRESS`：修复中。
* `FIXED`：已修复，等待验证。
* `REOPENED`：验证失败，重新打开。
* `CLOSED`：验证通过。
* `WONT_FIX`：当前版本不修复。
* `DUPLICATE`：与已有Bug重复。

# 13. Bug发现流程

发现问题后：

```text
记录Bug
→ 判断严重程度
→ 尝试复现
→ 将完整信息发给ChatGPT
→ ChatGPT分析
→ 生成Codex修复任务
→ Codex修复
→ 运行测试
→ 用户验证
→ 关闭Bug
````

不得发现Bug后直接让Codex：

```text
帮我把这个项目所有Bug修一下
```

应该一个Bug或一组强关联Bug对应一个修复任务。

---

# 14. Bug复现要求

确认Bug前，至少尝试：

1. 重复执行一次。
2. 刷新或重新进入页面。
3. 检查是否网络问题。
4. 检查终端错误。
5. 检查是否使用正确环境。
6. 检查是否为未保存代码。
7. 记录操作步骤。

若无法复现，状态可以保持：

```text
NEW
```

不要直接关闭。

# 16. Bug修复任务要求

Codex修复Bug时必须：

1. 先说明根本原因。
2. 尽量先增加失败测试。
3. 只修改必要文件。
4. 不顺手重构整个模块。
5. 修复后运行相关测试。
6. 执行回归测试。
7. 列出修改文件。
8. 说明是否存在数据修复需求。

---

# 17. 数据类Bug处理

以下Bug可能涉及数据库修复：

* 重复数据。
* 错误积分。
* 错误学习进度。
* 点赞数不一致。
* 评论数不一致。
* 错题重复。
* 对战重复结算。

处理流程：

```text
停止继续产生错误数据
→ 确认影响范围
→ 备份数据库
→ 修复代码
→ 编写数据修复脚本
→ 测试环境验证
→ 执行修复
→ 检查结果
```

不得直接手工修改正式数据而不留记录。

# 24. 任务与Bug关联

如果某个任务发现Bug，应在开发日志写：

```text
关联Bug：
- BUG-003
- BUG-004
```

Bug记录中写：

```text
关联任务：
- BATTLE-002
```

这样可以互相追踪。

# 25. Git与Bug关联

Bug修复提交建议：

```text
fix(battle): prevent duplicate score settlement
```

开发日志和Bug记录都需要保存Commit Hash。

若一个提交修复多个Bug，应写明：

```text
修复：
- BUG-011
- BUG-012
```

# 29. 不需要记录的内容

不需要在日志中记录：

* 每次鼠标点击。
