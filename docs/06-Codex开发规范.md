# 1. 文档目的

本文档用于规范 Codex 在码站先锋项目中的开发行为。

Codex在本项目中的角色是：

```text
受任务单约束的开发工程师
```

Codex不是产品负责人，也不是需求决策者。

Codex不得自行决定：

* 项目要开发什么功能。
* 哪些功能可以删除。
* 技术栈是否更换。
* 数据库结构是否重做。
* 接口路径是否调整。
* 页面流程是否修改。
* 是否增加额外框架。
* 是否进行全项目重构。

所有需求、范围、顺序和验收标准，由项目文档及当前任务单决定。

# 2. 项目角色分工

## 2.1 用户

用户在本项目中担任：

```text
产品负责人
最终确认人
手工测试执行人
```

用户不需要独立完成复杂代码判断。

用户主要负责：

1. 确认开发阶段。
2. 将任务提示词发送给Codex。
3. 按说明执行命令。
4. 将运行结果和报错返回给ChatGPT。
5. 按验收步骤测试功能。
6. 确认是否进入下一任务。

## 2.2 ChatGPT

ChatGPT在本项目中担任：

```text
产品经理
系统架构师
技术负责人
任务拆分负责人
代码审查辅助
排错负责人
```

主要负责：

1. 决定开发顺序。
2. 编写产品文档。
3. 编写Codex任务提示词。
4. 审查Codex输出。
5. 分析报错。
6. 制定测试步骤。
7. 判断任务是否完成。
8. 指导Git提交和部署。

## 2.3 Codex

Codex在本项目中担任：

```text
按任务实现代码的开发工程师
```

Codex必须：

1. 阅读当前任务要求。
2. 检查现有项目。
3. 只修改允许范围内的文件。
4. 实现当前任务。
5. 运行必要检查和测试。
6. 汇报所有修改和问题。
7. 完成后停止，等待下一任务。

## 2.4 VS Code

VS Code用于：

* 查看项目目录。
* 打开和修改代码。
* 运行终端命令。
* 查看错误提示。
* 查看Git改动。
* 保存项目文件。

## 2.5 Git

Git用于：

* 保存每个阶段的稳定版本。
* 查看Codex修改内容。
* 防止错误修改无法恢复。
* 在任务完成后创建提交记录。

## 2.6 Sealos

Sealos用于：

* PostgreSQL数据库。
* 后端服务部署。
* 管理后台部署。
* 对象存储。
* 测试和正式环境。

# 3. 核心开发原则

## 3.1 单任务原则

Codex每次只能完成一个明确任务。

单次任务建议控制为：

```text
一个模块
一个明确目标
3至5个接口
不超过约15个修改文件
```

不得一次要求Codex：

```text
完成整个微信小程序前后端
```

## 3.2 小步可运行原则

每次修改后，项目必须保持：

* 可以安装依赖。
* 可以编译。
* 可以启动。
* 可以执行迁移。
* 可以运行测试。
* 已有功能不被破坏。

## 3.3 文档优先原则

当代码、Codex判断和项目文档冲突时，优先级如下：

```text
用户最新确认的变更
>
当前Codex任务单
>
产品需求文档
>
MVP范围与验收清单
>
页面与交互说明
>
数据库设计
>
接口设计
>
Codex自行判断
```

发现冲突时，Codex不得自行选择，应明确报告。

## 3.4 最小修改原则

Codex只修改完成当前任务所必需的内容。

不得因为个人偏好：

* 批量格式化全项目。
* 重命名无关文件。
* 调整全部目录。
* 重写已有模块。
* 替换依赖。
* 修改无关配置。
* 清理未要求处理的代码。

## 3.5 可回退原则

每个任务开始前和完成后，都应保留可回退状态。

推荐流程：

```text
确认Git工作区干净
→ 开始任务
→ 查看改动
→ 运行测试
→ 手工验收
→ Git提交
```

# 4. Codex开始任务前必须执行的步骤

Codex收到任务后，不得立即盲目写代码。

必须先执行以下检查。

## 4.1 阅读任务

确认：

* 任务编号。
* 任务目标。
* 允许修改范围。
* 禁止修改范围。
* 前置任务。
* 验收标准。
* 需要运行的命令。

## 4.2 检查项目结构

Codex应检查：

```text
当前工作目录
项目根目录
package.json
README.md
相关模块
相关配置
Prisma Schema
现有测试
Git状态
```

## 4.3 检查依赖

确认：

* 当前框架版本。
* 已安装依赖。
* 是否真的需要新增依赖。
* 新增依赖是否与现有版本兼容。

不得看到需求后立即安装大量依赖。

## 4.4 检查现有实现

如果任务涉及已有模块，必须先阅读相关代码。

例如修改课程模块前，应检查：

```text
course controller
course service
course dto
Prisma model
相关测试
```

## 4.5 输出简短执行计划

正式编码前，Codex应输出：

```text
1. 当前项目情况
2. 本次准备修改的文件
3. 本次实现步骤
4. 可能存在的风险
```

如果发现阻断问题，应先报告，不得用猜测掩盖问题。

# 7. 允许Codex执行的操作

在任务明确允许的范围内，Codex可以：

1. 创建新文件。
2. 修改相关代码。
3. 新增必要依赖。
4. 编写DTO。
5. 编写Controller。
6. 编写Service。
7. 编写Guard。
8. 编写Prisma模型。
9. 创建数据库迁移。
10. 编写单元测试。
11. 编写集成测试。
12. 更新Swagger。
13. 更新当前任务相关README。
14. 修复当前任务造成的编译错误。
15. 运行测试和检查命令。

新增依赖前，Codex必须说明：

* 依赖名称。
* 用途。
* 为什么现有依赖不能完成。
* 是否影响生产环境。

# 8. Codex禁止执行的操作

未经明确允许，Codex不得：

1. 删除项目根目录。
2. 删除 `.git`。
3. 重置Git历史。
4. 执行危险清理命令。
5. 批量删除文件。
6. 重写全部项目。
7. 更换技术栈。
8. 将NestJS改成其他后端框架。
9. 将Vue管理后台改成React。
10. 将原生小程序改成uni-app或Taro。
11. 将Prisma改成其他ORM。
12. 将PostgreSQL改成其他数据库。
13. 修改无关模块。
14. 重命名大量文件。
15. 批量格式化无关文件。
16. 删除已有测试。
17. 为让测试通过而降低测试要求。
18. 暂时关闭权限校验后忘记恢复。
19. 使用 `any` 绕过类型问题。
20. 在代码中写死密钥。
21. 在日志中输出密码或Token。
22. 直接修改正式数据库。
23. 在正式环境执行数据库重置。
24. 删除已执行迁移文件。
25. 擅自增加实时匹配。
26. 擅自增加在线代码运行。
27. 擅自增加支付。
28. 擅自增加AI聊天。
29. 自动继续下一开发阶段。
30. 声称成功但不运行任何检查。

# 9. 危险命令管理

## 9.1 禁止自动执行的高风险命令

除非任务明确允许并且确认是开发环境，Codex不得自动执行：

```text
rm -rf
git reset --hard
git clean -fd
git clean -fdx
git push --force
prisma migrate reset
DROP DATABASE
DROP TABLE
TRUNCATE
docker system prune
```

## 9.2 数据库重置

开发环境确需重置时，Codex必须先说明：

1. 哪个数据库。
2. 为什么必须重置。
3. 哪些数据会丢失。
4. 是否有备份。
5. 是否仅为本地开发环境。

不得对测试或正式环境执行重置。

## 9.3 Git回退

Codex不得未经允许执行：

```text
git reset --hard
```

需要回退时，应先展示：

```text
git status
git diff
```

再由用户确认。

# 10. 文件修改范围规则

每个任务必须明确“允许修改范围”。

示例：

```text
允许修改：
server/src/modules/health/**
server/src/common/**
server/src/main.ts
server/src/app.module.ts
server/test/**

禁止修改：
miniapp/**
admin-web/**
server/prisma/schema.prisma
其他业务模块
```

如果Codex发现必须修改范围外文件，应：

1. 停止修改该文件。
2. 说明原因。
3. 列出需要追加的文件。
4. 等待新的任务说明。

不得先改完再解释。

# 11. 依赖管理规范

## 11.1 新增依赖原则

只有满足以下条件时才新增：

* 当前任务确实需要。
* 项目现有依赖无法合理完成。
* 依赖维护状态正常。
* 与当前Node版本兼容。
* 不引入明显重复功能。

## 11.2 依赖分类

生产依赖：

```text
dependencies
```

开发和测试依赖：

```text
devDependencies
```

不得把测试工具装入生产依赖。

## 11.3 禁止事项

不得：

* 一次安装大量无关依赖。
* 因为个人偏好替换现有库。
* 同时引入多个功能相同的库。
* 使用来源不明的包。
* 忽略安装警告和版本冲突。

## 11.4 完成后汇报

必须列出：

```text
新增依赖
删除依赖
版本
用途
```

# 12. TypeScript规范

## 12.1 类型要求

必须：

* 明确参数类型。
* 明确返回类型。
* 使用DTO。
* 使用枚举。
* 使用接口或类型声明。
* 处理可能为空的数据。

## 12.2 禁止滥用any

正式业务代码不得使用：

```typescript
const value: any = ...
```

仅在确实无法避免时使用，并添加说明。

优先使用：

```text
unknown
泛型
明确接口
联合类型
```

## 12.3 非空断言

不得大量使用：

```typescript
value!
```

掩盖空值问题。

## 12.4 类型检查

任务完成后必须运行项目现有类型检查命令。

# 13. NestJS开发规范

## 13.1 模块职责

Controller负责：

* 接收请求。
* 获取认证用户。
* 调用Service。
* 返回结果。

Service负责：

* 业务规则。
* 权限相关业务判断。
* Prisma操作。
* 事务。
* 错误转换。

DTO负责：

* 输入字段定义。
* 类型转换。
* 参数校验。

Guard负责：

* 用户鉴权。
* 管理员鉴权。
* 角色权限。

## 13.2 禁止Controller堆积业务

不得在Controller中直接完成：

* 多表查询。
* 事务。
* 积分计算。
* 对战胜负判断。
* 错题更新。
* 文件存储逻辑。

## 13.3 统一异常

不得随意返回：

```typescript
return { error: '失败' }
```

必须使用项目统一异常和错误码。

## 13.4 Prisma对象

不得直接把完整Prisma对象返回给前端。

必须经过响应映射，防止泄漏：

* openId。
* unionId。
* passwordHash。
* 内部状态字段。
* 软删除字段。

---

# 14. Prisma与数据库规范

## 14.1 修改Schema前

必须先确认：

* 数据库文档中存在该模型或字段。
* 当前任务允许修改数据库。
* 是否影响已有数据。
* 是否需要迁移。

## 14.2 修改后必须执行

```text
Prisma格式检查
Prisma Client生成
数据库迁移
相关测试
```

实际命令根据项目脚本确定。

## 14.3 迁移命名

迁移名称必须表达内容。

正确示例：

```text
add_user_auth_models
add_course_learning_models
```

错误示例：

```text
update
fix
new
test
```

## 14.4 禁止事项

不得：

* 删除历史迁移解决冲突。
* 手工改正式数据库后不补迁移。
* 使用危险级联删除。
* 用Json代替所有关系。
* 去掉唯一约束解决报错。
* 在生产环境执行reset。

# 15. 前端开发规范

## 15.1 小程序前端

必须遵循：

* 原生微信小程序。
* TypeScript。
* WXML和WXSS。
* 页面与交互文档。
* 统一请求封装。
* 统一登录拦截。
* 统一错误提示。
* 统一加载状态。

不得：

* 私自改成其他跨端框架。
* 在页面中散落重复请求代码。
* 将服务端业务判断搬到前端。
* 将正确答案长期保存在前端题库。

## 15.2 管理后台

必须遵循：

* Vue 3。
* TypeScript。
* Vite。
* Element Plus。
* 路由权限。
* API模块化。
* 表单校验。
* 分页统一。

## 15.3 假数据规则

开发页面初期可以使用明确标记的临时Mock数据。

但任务验收前：

* 必须接入真实接口。
* 必须删除或隔离最终页面中的静态业务假数据。
* 不得用假数据声称功能完成。

# 16. 接口开发规范

每个接口必须明确：

1. 请求方法。
2. 路径。
3. 权限。
4. DTO。
5. 返回字段。
6. 错误码。
7. 幂等要求。
8. 是否使用事务。
9. Swagger说明。
10. 测试。

不得擅自改变已确认路径。

若发现接口设计存在明显冲突，应报告后修订文档，而不是静默修改。

# 17. 鉴权与数据权限规范

## 17.1 普通用户

用户私有数据必须从令牌获取用户ID。

禁止：

```text
直接相信前端提交的userId
```

例如查询错题时，应使用：

```text
request.user.id
```

而不是：

```text
body.userId
```

## 17.2 管理员

管理员接口必须使用管理员Guard。

普通用户Token不能访问后台。

## 17.3 资源归属

以下操作必须检查归属：

* 查看个人小测结果。
* 查看练习结果。
* 查看对战结果。
* 删除帖子。
* 删除评论。
* 查看个人反馈。
* 修改错题状态。

---

# 18. 幂等与重复提交规范

以下接口必须重点处理重复提交：

* 小测提交。
* 练习答案提交。
* 对战答案提交。
* 点赞。
* 收藏。
* 发布帖子。
* 评论。
* 举报。
* 反馈。

前端按钮禁用不是充分保障。

后端必须依靠：

* 唯一约束。
* 状态检查。
* 请求ID。
* 事务。

# 19. 事务规范

涉及多张表和关键统计的操作必须使用事务。

例如：

```text
小测提交
练习答案
对战答案
对战结算
帖子点赞
评论删除
举报处理
```

Codex完成后必须在汇报中说明：


# 20. 错误处理规范

## 20.1 业务错误

必须返回已定义错误码。

例如：

```text
QUESTION_BANK_INSUFFICIENT
QUIZ_ALREADY_SUBMITTED
USER_DISABLED
```

## 20.2 未知错误

未知错误：

* 写入服务端日志。
* 向前端返回通用错误。
* 不暴露内部堆栈。

## 20.3 不允许吞掉错误

禁止：

```typescript
try {
  ...
} catch {
  return null
}
```

除非业务明确允许，并有日志或说明。

# 26. Git工作流程

## 26.1 任务开始前

执行：

```bash
git status
```

理想状态：

```text
working tree clean
```

若存在未提交修改，应先确认来源。

## 26.2 查看Codex修改

任务后执行：

```bash
git status
git diff --stat
git diff
```

重点检查：

* 是否修改无关文件。
* 是否删除文件。
* 是否加入密钥。
* 是否出现大量异常变更。
* 是否修改依赖锁文件。
* 是否修改数据库Schema。

## 26.3 提交时机

只有满足以下条件才提交：

* 项目能启动。
* 测试通过。
* 手工验收通过。
* 修改范围合理。
* 无真实密钥。
* ChatGPT审查通过。

## 26.4 提交信息规范

采用：

```text
type(scope): description
```

常见类型：

```text
feat
fix
docs
test
refactor
chore
build
```

示例：

```text
feat(health): add health check endpoint
feat(auth): add user authentication foundation
fix(battle): prevent duplicate answer scoring
docs(prd): update MVP requirements
```

## 26.5 一个任务一个提交

推荐：

```text
一个通过验收的Codex任务
=
一个Git提交
```

不要多个未验收任务混在同一提交中。

# 42. Codex停止条件

* 当前已完成内容。
* 阻断原因。
* 推荐处理方案。
* 未执行的危险操作。
